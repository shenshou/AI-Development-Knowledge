# 跨网站油猴脚本开发经验与工程规范

> 版本：1.0  
> 整理日期：2026-11-19  
> 来源案例：MyOnlineTools 项目中的 JavDB 评论批量搜索脚本与 LTX 批量检测脚本  
> 本文定位：可复用的工程参考与检查清单，不是所有油猴脚本都必须遵守的固定架构。

## 1. 目标与适用范围

本文沉淀两个真实网站脚本的开发经验，帮助未来开发其他网站的用户脚本时，更系统地调查页面与接口、处理认证和数据、设计批量任务、控制请求频率、分类错误并完成真实验证。

**重要边界：本文提供的是可选择、可裁剪的工程方法，不是技术限制。**

- 不要求所有脚本都必须调用 API。DOM 操作、页面增强、自动填表、快捷键、样式调整等简单脚本，可能根本不需要接口层或任务队列。
- 不要求所有脚本都必须独立运行、使用相同 UI、采用相同目录结构或相同技术栈。
- 不要求其他网站复制 JavDB 或 LTX 的认证、签名、加密、分页、请求间隔或接口方案。
- 不为了套规范而增加不必要的抽象、配置、状态管理、依赖或文件拆分。
- 应先理解当前网站、用户目标和运行环境，再选择最简单且可靠的实现。
- 网站条款、权限、隐私、安全边界和明确的用户要求优先于案例中的实现细节。

适用场景包括但不限于：网站页面增强、数据提取、批量查询、评论/资源检索、表单辅助、内容整理、跨页面工作流。具体任务只采用相关章节。

## 2. 核心工程原则

### 2.1 先调查，再设计

实现前先确认：
1. 用户真正要解决的问题、输入输出和成功标准。
2. 脚本运行在哪个页面、域名、页面状态及浏览器环境。
3. 网站是否已有可用的页面数据、DOM、前端状态或官方接口。
4. 是否需要登录、权限、CSRF、签名、加密或其他会话上下文。
5. 请求是否分页、是否有频率限制、是否可能触发风控。
6. 结果如何验证，哪些情况不能被误判为成功。

不要从猜测接口、复制其他网站实现或直接编写请求代码开始。

### 2.2 选择合适的集成方式

按任务选择，不设唯一答案：
- **DOM 优先**：目标数据已在页面上，或任务本质是页面交互/增强时，直接读取或操作 DOM 往往更简单。
- **复用页面现有数据**：页面已加载所需状态或数据时，评估是否可以安全、稳定地复用。
- **网站接口**：批量数据、分页或页面未展示的数据可能更适合接口，但必须先理解接口契约及权限边界。
- **混合方式**：例如用页面定位作品，再用接口读取评论；或用页面现有会话调用同源接口。

优先采用稳定、最小权限、与网站正常交互一致的方式。不要为了“技术先进”而强行使用 API。

### 2.3 保持职责清晰，避免过度工程化

当复杂度确实需要时，可将输入解析、接口适配、数据规范化、任务调度、结果展示分开。简单脚本则可以保持单文件和直接结构。

拆分依据应是职责边界、复用价值、测试需求和变化频率，而不是文件行数或追求抽象数量。避免无必要的全局状态、重复状态源和隐式耦合。

## 3. 网站与接口调查

若任务需要接口，至少确认以下内容：

- 请求方法、路径、参数、请求头、Content-Type。
- 请求来源、同源关系、重定向行为及浏览器 CORS 限制。
- 请求是否依赖当前登录会话、CSRF token、签名或动态参数。
- 响应状态码、响应结构、业务成功标志及错误结构。
- 分页方式：页码、游标、总数、是否有下一页，以及分页一致性。
- 排序、筛选、去重、大小写和编号规范化规则。
- 速率限制、Retry-After、验证码、挑战页和其他访问限制。
- 接口是否为公开/官方支持接口，是否存在使用限制。

建议使用浏览器开发者工具观察正常页面行为。HAR、Network、Console 等材料可能含 Cookie、Authorization、查询参数或个人数据；分享前应脱敏，只提供排查所需内容。不要要求用户把密码、Cookie 或 Token 发给 AI。

**接口契约应以实际观察和验证为准。** 不要把某一次成功响应视为永久稳定，也不要根据一个字段名猜测完整语义。

## 4. 登录态、签名、加密与响应处理

这些机制高度依赖具体网站，只能复用调查方法，不能复用某个网站的实现细节。

### 4.1 认证边界

- 明确请求是否需要当前页面已有的登录态，以及凭据由浏览器如何附带。
- 优先使用网站正常页面上下文中已有的会话机制，不复制、导出或持久化敏感凭据。
- 仅在必要范围内发送凭据；避免把站点 Cookie 带到不需要它的接口或第三方域名。
- 不在脚本日志、界面、剪贴板或持久化存储中暴露 Token、Cookie、密码。
- 权限不足、需要登录或会话失效时，应清晰提示用户，而不是尝试绕过。

### 4.2 签名与加密

若网站协议确实使用签名或加密：
1. 从可观察的正常客户端流程确认算法、参数来源、编码、密钥派生和时序。
2. 区分认证、完整性校验、加密、压缩等不同环节。
3. 逐层验证输入输出，避免把解密失败误报成空数据。
4. 不硬编码用户秘密，不伪造权限，不绕过访问控制或挑战机制。
5. 将网站专属协议封装在该网站的适配层中，并记录适用版本和验证依据。

**案例专属信息，不是通用要求：**
- JavDB 案例沿用其既有 Reviews API 签名逻辑；影片搜索使用 JavDB 页面同源会话，Reviews API 不携带 JavDB Cookie。
- LTX 案例按网站前端协议处理 ECDH P-256、HKDF-SHA256、AES-256-GCM 响应解密及 Gzip 解压。
- 新网站必须重新调查其协议。不得默认其他网站也使用上述算法或流程。

### 4.3 响应解析

- 先检查 HTTP 状态，再解析响应体；HTTP 成功不等于业务成功。
- 校验必要字段、类型、空值和业务成功标志。
- 对压缩、编码、加密的响应逐层处理，并为每一层提供可诊断错误。
- 对异常结构采取失败关闭策略，不把未知响应当作空结果或成功结果。

## 5. 数据正确性与分页

数据正确性优先于速度和界面上的“完成”提示。

- 使用明确的规范化规则处理大小写、空格、分隔符和编号格式。
- 尽量做精确匹配，避免模糊匹配把无关内容误认为目标。
- 将“存在”“不存在”“无法确认/检测失败”分开表达。
- 只有在所有必要分页均成功读取、分页元数据合理且结果完整时，才能据此判定不存在。
- 分页过程中若总数、游标或快照不一致，应报告不确定或重试有限次数，不应静默给出确定结论。
- 去重必须基于稳定标识，不能只凭展示文本。
- 核心结果与附加信息分离：附加资源、图片、评论详情等获取失败，不应推翻已经确认的核心结果。
- 保留必要的原始错误上下文，便于诊断，但不要泄露敏感信息。

## 6. 批量任务与请求调度

仅当任务确实涉及多个请求或长时间运行时采用本章。

### 6.1 任务状态

建议明确区分：
- 待处理
- 运行中
- 暂停中
- 已完成
- 已停止
- 部分完成/存在失败

暂停、继续、停止应有清晰语义。停止后不应继续发起新请求；正在进行的请求是否可取消，取决于所用 API 和实现方式。

### 6.2 队列与节流

- 默认从串行或低并发开始，依据网站行为和实际测试再决定是否并发。
- 请求间隔、批次大小应基于网站限制和任务体验设置，不存在通用固定值。
- 对批量输入设置合理上限，避免误操作导致大量请求。
- 支持分批处理和进度反馈；必要时允许用户暂停或停止。
- 不通过并发、代理轮换或其他方式规避网站限流和访问控制。

### 6.3 生命周期与状态存储

- 明确刷新、关闭标签页、导航离开时任务如何处理。
- 仅在确有恢复需求时持久化任务；默认优先使用内存状态，减少隐私和过期状态风险。
- 持久化前说明保存内容、位置、生命周期和清除方式。
- 设置项与任务数据分开管理；设置存储应尽量少且可解释。

## 7. 错误分类、重试与风控边界

不要把所有异常都显示成“请求失败”，也不要无限重试。

| 情况 | 建议处理 |
|---|---|
| HTTP 401 / 需要登录 | 提示登录或会话失效；停止依赖该会话的后续任务 |
| HTTP 403 / 权限拒绝 | 暂停或停止相关队列，提示权限/风控；不循环重试 |
| Cloudflare 或其他 Challenge | 明确提示需要用户正常完成网站验证；不自动绕过 |
| HTTP 429 | 尊重 Retry-After；等待超过合理上限时转为手动暂停 |
| HTTP 5xx | 可对幂等请求做有限次数退避重试 |
| 网络中断 / 超时 | 有限重试，并区分最终失败与空结果 |
| 业务错误 | 根据业务错误码分类，不因 HTTP 200 就视为成功 |
| 响应结构变化 | 报告协议/兼容性错误，不静默吞掉 |
| 解密/解压失败 | 单独报告处理阶段，避免误报为“没有数据” |

重试前先判断请求是否幂等、失败是否可能由用户操作或风控引起。退避策略应有最大次数和最大等待时间。重试不能成为规避网站限制的手段。

## 8. UI 与用户体验

- 让用户知道当前输入、进度、成功、失败和不确定状态。
- 对长任务提供暂停、继续、停止（若任务支持）。
- 区分单条结果和批量汇总，避免大量内容挤成长页面。
- 提供复制、导出等操作时，明确其作用范围和筛选条件。
- 对配置项给出合理默认值；不要为了可配置而暴露过多低价值选项。
- 错误消息应说明发生阶段、可采取的下一步；避免只显示原始堆栈。
- 不用“成功”掩盖部分失败；批量任务应呈现部分完成情况。
- UI 应与目标网站风格和脚本体量相匹配，不要求所有脚本复用同一面板。

## 9. 安全、隐私与存储

- 最小化权限声明和匹配域名范围。
- 不读取或收集与任务无关的用户数据。
- 不要求用户提交账号密码、Cookie、Token。
- 不把会话凭据发送到第三方域名。
- 默认不上传用户输入、查询记录或结果到远程服务。
- 谨慎使用 localStorage、IndexedDB、GM_setValue 等持久化能力；只存必要设置或用户明确需要保留的数据。
- 对复制、导出、日志和错误报告做敏感信息检查。
- 对来自网页、接口或用户输入的数据进行安全处理；将其作为不可信数据，不执行任意 HTML/脚本。
- 不绕过登录、付费墙、验证码、风控、访问控制或其他安全机制。

## 10. 测试与验证

自动化测试和真实网站验证解决不同问题，不能互相替代。

### 10.1 静态与自动化检查

按脚本复杂度选择：
- 语法检查、Lint、构建检查。
- 输入解析、规范化、精确匹配、分页合并、错误分类的单元测试。
- 使用模拟响应测试正常、空数据、异常结构、401/403/429/5xx、超时等路径。
- 对 UI 状态和复制范围进行必要测试。
- 不要为了小型脚本引入维护成本明显高于收益的测试基础设施。

### 10.2 真实浏览器验证

涉及真实网站、登录态、浏览器权限、CORS、动态签名或加密时，应在用户授权和正常账号环境下验证：
- 脚本是否正确匹配页面并注入。
- 正常数据、无数据、特殊输入、批量输入。
- 分页完整性与结果准确性。
- 登录失效、权限拒绝、限流和网络异常。
- 暂停/继续/停止和刷新/关闭后的行为。
- 复制、展开、筛选等用户操作。
- 与网站现有功能是否冲突。

记录测试环境、日期、脚本版本和结果。网站可能变化，历史成功不能保证未来始终有效。

### 10.3 验证结论分级

- **静态通过**：代码结构和基础检查通过。
- **模拟通过**：模拟数据和错误路径通过。
- **真实网站验证通过**：在指定网站环境下完成真实操作。
- **用户验收通过**：用户实际安装运行并确认符合预期。

不得把静态检查或模拟测试描述成真实网站验证。

## 11. 版本管理与发布

建议流程：
1. 明确需求和验收标准。
2. 调查页面与接口，形成技术假设。
3. 实现最小可验证版本。
4. 静态检查和自动化测试。
5. 在真实网站环境验证。
6. 处理反馈并复测。
7. 更新版本号、变更记录和安装/更新说明。
8. 通过分支与 Pull Request 审查后合并。
9. 确认正式文件和更新地址可用，再通知用户更新。
10. 记录已知限制和回滚方式。

对于独立发布的用户脚本，可采用稳定的 Raw 文件地址，使脚本更新与网站本身部署解耦。是否拆成独立脚本、是否使用单文件、是否通过 PR 发布，应由项目需求决定。

## 12. 两个实践案例

### 12.1 JavDB 评论批量搜索脚本

实践特点：
- 独立运行于 JavDB 页面；在线工具箱中原有评论搜索页面仍保留。
- 影片搜索使用当前 JavDB 页面同源会话；Reviews API 使用既有签名逻辑且不携带 JavDB Cookie。
- 串行请求，默认 8 秒间隔，可选 5/8/10/15 秒；每页默认 20 条评论，可选 40 条。
- 支持关键词、起始日期筛选、按番号展开评论、批量复制筛选结果。
- 支持暂停、继续、停止；运行状态保存在页面内存，刷新或关闭标签页会终止任务。
- 搜索错误与 Reviews API 错误分开标识。
- 403 暂停队列，不循环自动重试；Challenge 明确提示。
- 429 遵循 Retry-After；超过自动等待上限后转为手动暂停。
- 网络错误和常见 5xx 最多有限重试 2 次并递增等待。
- 不读取、保存或要求用户提供账号密码、Cookie、Token。

可迁移经验：同源会话边界、接口职责分离、限流策略、队列状态、错误分类、按番号组织大量结果，以及真实浏览器验收。

不可直接迁移：JavDB 的接口路径、签名算法、评论数据结构、请求间隔和具体风控行为。

### 12.2 LTX 批量检测脚本

实践特点：
- 独立运行于 LTX 官方网站，不依赖工具箱、Gateway、弹窗或跨页面消息桥接。
- 使用网站同源相对路径请求，并按网站正常前端协议处理响应。
- 按规范化后的 `item.code` 精确匹配；完整检查分页且分页元数据一致后才判定不存在。
- 支持每行一个番号及空格、逗号、分号分隔；单批最多 300 个，逐个查询。
- 请求间隔可选 1/3/5/8/10/15 秒，默认 1 秒。
- 存在性结果分为存在、不存在、检测失败；失败不视为不存在。
- 存在性检测与资源链接获取分离；资源接口失败不改变已确认的存在性结果。
- 资源接口按每批最多 60 个番号获取作品对象，从 `items[].link` 读取链接。
- 区分 magnet 与 ed2k，支持单条复制和按类型批量复制。
- 可选精简 ed2k 文件名，默认关闭；无法安全识别时保留原链接。
- 403 停止剩余批次；429 遵循 Retry-After，不绕过访问限制。
- 结果仅保存在页面运行期间内存；精简 ed2k 设置单独保存在浏览器本地。

可迁移经验：精确匹配、完整分页校验、核心结果与附加资源分离、失败状态不等于不存在、分批处理和不同资源类型的结果操作。

不可直接迁移：LTX 的接口路径、ECDH/HKDF/AES-GCM/Gzip 协议、快照参数、批次上限和具体链接格式。

## 13. 新网站脚本开发检查清单

按任务勾选适用项；不适用的项目可以跳过。

### 需求与范围
- [ ] 已明确用户目标、输入、输出和验收标准。
- [ ] 已确认脚本运行页面、域名和浏览器环境。
- [ ] 已选择最简单合适的实现方式，没有为了套规范而过度设计。

### 页面与接口
- [ ] 已确认数据来自 DOM、页面状态、接口或混合来源。
- [ ] 如使用接口，已确认请求方法、参数、认证、响应和业务错误。
- [ ] 已确认分页、排序、筛选和数据规范化规则。
- [ ] 已评估 CORS、同源、浏览器权限及接口稳定性。

### 安全与隐私
- [ ] 权限和匹配域名遵循最小化原则。
- [ ] 没有要求或记录用户密码、Cookie、Token。
- [ ] 没有向不必要的第三方发送会话凭据。
- [ ] 存储内容、生命周期和用途明确。
- [ ] 没有绕过登录、验证码、风控或访问控制。

### 正确性与可靠性

## 14. 如何使用本文

- 把本文作为新网站用户脚本开发时的参考手册，而不是强制模板。
- 只加载与当前任务相关的章节。
- 先根据网站实际情况做技术判断，再决定采用哪些建议。
- 若案例经验与新网站的官方协议、实际行为或用户需求冲突，以新网站的事实和用户需求为准。
- 新项目验证出的通用经验可以补充到本文；网站专属信息应放在独立案例中，避免污染通用规范。

**最终原则：复用调查方法、工程判断和可靠性经验，不复用未经验证的网站专属实现；帮助 AI 做出更好的技术选择，而不是限制 AI 的技术选择。**
