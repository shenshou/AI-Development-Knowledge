# Fork 项目改造与 GitHub Actions 工程实践规范

> 版本：1.0  
> 整理日期：2026-11-21  
> 来源案例：`shenshou/mpc-hc-next`（基于 `clsid2/mpc-hc` Fork，集成 MPC Video Renderer 并修复 GitHub Actions 工作流）  
> 文档定位：可复用的工程参考、排障方法与验收清单；不是所有 Fork 项目都必须采用的固定流程。

## 1. 目标与适用范围

本文总结接手陌生开源 Fork、进行定制改造、维护 CI、生成构建产物和验证交付时的经验。重点解决以下问题：

- 如何先理解上游项目和 Fork 的现状，避免盲目修改。
- 如何控制改造范围，降低与上游后续同步的冲突。
- 如何安全地调整 GitHub Actions，避免反复试错和浪费构建时间。
- 如何管理外部依赖、构建矩阵、架构差异和打包路径。
- 如何从“工作流绿色”走到“产物正确、软件实际可用”。

**本文是按需采用的工程参考，不是强制模板。** 小型项目不需要照搬大型项目的目录、测试矩阵或自动化设施；应根据语言、构建系统、风险和交付形式选择必要步骤。

## 2. 核心原则

### 2.1 先调查，再修改

动手前确认：
1. 上游仓库、当前 Fork、默认分支和实际开发分支分别是什么。
2. 当前分支相对上游有哪些提交和文件差异。
3. 项目使用什么语言、构建系统、依赖管理和发布方式。
4. CI 工作流由什么事件触发，构建在哪些 Runner/系统环境执行。
5. 最终交付物是什么，如何生成、命名、验证和下载。
6. 用户明确要求修改什么，以及哪些范围明确不允许改动。

不要因为看到一个失败的 Actions 运行，就直接开始修改源代码或工作流。先建立“现状—目标—差异—验证方式”的对应关系。

### 2.2 明确改造边界

开始前列出：
- **必须修改**：完成目标所必需的文件和步骤。
- **允许修改**：为实现目标可能需要调整的辅助文件。
- **明确不改**：用户指定保留的核心代码、上游行为、发布方式等。
- **暂不处理**：与当前目标无关、收益不明确或风险过高的事项。

优先采用最小改动。不要顺手重构无关代码、升级无关依赖、删除看似多余的 CI 步骤或改变上游默认行为。任何清理都应先证明该内容确实无用且不影响构建、运行、打包或维护。

### 2.3 保持变更可审查、可回退

- 尽量让一个提交只解决一个明确问题。
- 工作流修复、依赖接入、源代码修改和文档更新尽量分开。
- 提交前检查变更文件列表和 diff，确认没有意外文件。
- 保留原始失败信息和修复前后的运行链接。
- 不通过强制推送覆盖他人或上游历史，除非明确需要并获得授权。
- 不擅自创建 Release、发布包或修改用户未授权的分支。

### 2.4 不把“CI 通过”当成“软件正确”

验证应分层进行：
1. 工作流能被 GitHub 识别并创建 Job。
2. Job 的每个步骤完成。
3. Artifact 确实生成。
4. Artifact 可下载、可解压，内容和架构正确。
5. 安装包内部确实包含预期文件。
6. 软件在目标环境中能启动并完成关键功能。
7. 用户实际测试并验收。

只能声称已经完成证据支持的层级。

## 3. 接手 Fork 项目的标准调查

### 3.1 仓库与分支

记录：
- 上游仓库 URL、Fork 仓库 URL。
- 上游默认分支、Fork 默认分支、当前工作分支。
- Fork 与上游的 ahead/behind 情况。
- 当前工作区是否干净，有无用户未提交修改。
- 最近相关提交、已有定制改动和历史 CI 失败。

不要默认 Fork 的默认分支就是开发分支，也不要默认 Fork 与上游仍保持同步。

### 3.2 项目构建结构

按项目实际情况调查：
- 入口脚本、解决方案、工程文件、构建脚本。
- Debug/Release、x86/x64/ARM 等配置。
- 依赖下载、缓存、工具链安装和版本选择。
- 编译产物的原始目录、重命名、复制、压缩和安装包制作步骤。
- 安装器脚本、资源文件、便携版目录和运行时依赖。
- CI 与本地构建是否存在环境差异。

尤其要追踪一个文件从“依赖下载”到“最终用户拿到的包”的完整路径。只在构建日志中看到依赖下载成功，不代表它进入了最终安装包或便携包。

### 3.3 基线与验收标准

修改前先记录可比较的基线：
- 当前成功/失败的构建运行。
- 当前产物名称、数量、大小和目录结构。
- 用户当前能否正常安装、启动和使用。
- 本次改造后必须满足的检查项。

验收标准应尽量具体，例如“x86 便携包包含 x86 组件，x64 便携包包含 x64 组件”，而不是笼统写“支持该组件”。

## 4. GitHub Actions 排障：先判断失败发生在哪一层

这是本次 MPC-HC 项目最重要的经验。Run #16–#19 连续失败，页面没有 Job、没有步骤日志、没有 Artifact；一开始不能据此判断为编译错误。最终检查发现 `.github/workflows/build.yml` 文件尾部存在重复且破坏结构的片段。清理后 Run #20 成功完成构建并产出四个目标包。

### 4.1 先读取运行元数据，不要先重跑

每次失败先收集：
- Workflow 名称和 Workflow 文件路径。
- Run ID、触发事件、分支、commit SHA。
- Run 的 conclusion/status。
- 是否创建 Job；每个 Job 的 conclusion。
- Job 是否有步骤日志，失败发生在哪一步。
- 是否产生 Artifact；Artifact 数量和名称。
- 是否存在 annotation、check run 或 GitHub 解析错误信息。

**不要只看 Actions 列表里的红色叉号。** 红色叉号只说明运行没有成功，不能说明失败发生在 YAML 解析、Runner 启动、依赖安装、编译还是打包阶段。

### 4.2 失败层级判断表

| 观察结果 | 优先调查方向 | 不应立即做的事 |
|---|---|---|
| Run 失败，Job 数量为 0 | Workflow YAML 解析、工作流文件结构、触发条件、事件过滤、GitHub 是否接受该工作流 | 不要直接修改 C++/业务源代码 |
| Job 已创建，但 Runner 未正常启动 | Runner 标签、系统镜像、并发/配额、权限、环境初始化 | 不要先改编译参数 |
| Job 启动，早期步骤失败 | checkout、权限、工具链、环境变量、网络或依赖安装 | 不要把问题归咎于最终打包 |
| 下载依赖失败 | URL、上游发布资产、网络、限流、资产重命名、校验值 | 不要无验证地换成“latest” |
| 编译步骤失败 | 编译器版本、SDK、构建参数、源码变更、依赖头文件/库 | 不要通过删除失败步骤让 CI 变绿 |
| 编译成功、打包失败 | 文件路径、架构映射、安装器脚本、压缩命令、缺失文件 | 不要只检查 EXE 是否存在 |
| Artifact 上传失败 | 路径、通配符、文件是否存在、权限、Artifact 配置 | 不要误判为编译失败 |
| Artifact 成功但软件异常 | 产物内容、运行时依赖、安装器行为、架构和目标环境 | 不要以 CI 绿色作为最终验收 |

以上是排障优先级，不是绝对诊断。必须以实际日志、元数据和复现结果为依据。

### 4.3 Job 为 0 时的检查顺序

当 Run 没有 Job、步骤日志和 Artifact 时，优先按以下顺序检查：

1. **工作流文件是否被 GitHub 识别**：路径是否位于 `.github/workflows/`，扩展名是否为受支持的 YAML 扩展名。
2. **YAML 结构是否有效**：缩进、冒号、列表、映射、引号、表达式、块标量是否正确。
3. **文件是否存在重复或残留内容**：尤其检查文件尾部是否有复制粘贴产生的重复 Job、重复步骤、孤立的 `steps:`、`jobs:` 或多余片段。
4. **触发事件是否匹配**：检查 `on`、分支过滤、路径过滤、手动触发配置及实际事件类型。
5. **条件是否阻止 Job 创建**：检查 `if`、矩阵配置、依赖 Job 和动态输出。
6. **查看 GitHub 对该 commit 的工作流/check 信息**：确认工作流是否被解析和接受。

不要把“没有 Job”自动等同于 YAML 错误；触发条件、权限、工作流识别和 GitHub 平台状态也可能导致类似表象。应逐项排除并记录证据。

### 4.4 检查工作流文件时的重点

- 从文件第一行检查到最后一行，不要只看报错附近。
- 检查是否存在意外重复的完整代码块或尾部残片。
- 检查每个 `jobs`、Job、`steps`、条件块和脚本块的层级关系。
- 检查 YAML 多行字符串（`|`、`>`）是否正确闭合和缩进。
- 检查表达式语法、变量引用和矩阵引用。
- 检查 `if` 条件、Job 依赖关系和输出引用。
- 对照修改前后的 diff，确认不是为了修一个语法问题而删除了有效步骤。

建议使用 YAML 解析器和 Action 专用静态检查工具（例如 actionlint）。PowerShell 脚本较复杂时，也应单独做语法或静态检查。工具是否可用取决于环境；没有执行检查就不能声称“已通过 lint”。

### 4.5 修复后如何验证

- 先审查完整文件和 diff。
- 确认只修复已定位的问题，没有顺手删减构建步骤。
- 能做静态检查时先做静态检查。
- 再运行工作流，确认 Job 已创建。
- 查看每个 Job 的步骤结论和日志，而不只是 Run 总状态。
- 记录修复 commit SHA，确保运行确实使用了该提交。
- 成功后检查 Artifact，并继续做内容级验证。

**禁止无依据的反复重跑。** 每次重跑前都应明确：上一轮失败原因是什么、这次修改了什么、预期哪个症状会改变。如果没有新的证据或代码变化，重跑通常没有诊断价值。

## 5. 工作流修改的工程方法

### 5.1 先理解现有流程

沿着完整链路读工作流：
触发条件 → Runner → checkout → 工具链 → 依赖 → 编译 → 后处理 → 安装包/便携包 → 验证 → Artifact 上传。

不要只读某一个失败步骤。某一步可能依赖前面步骤的工作目录、环境变量、缓存、文件命名或架构矩阵。

### 5.2 最小化修改，保留有效步骤

- 不因耗时而擅自删除现有构建、测试、验证或打包步骤。
- 不随意更换 Runner 镜像或工具链版本。
- 不为了绕过错误而把失败命令改成允许失败。
- 不用固定延迟替代真正的依赖关系或健康检查。
- 不将多个不同问题塞进一次大规模工作流重写。
- 对工作流行为有影响的改动，尽量使用独立提交，便于定位回归。

### 5.3 将复杂脚本拆成可诊断步骤

适当把下载、校验、解压、文件检查、复制、构建和产物验证分成独立步骤。每一步应：
- 输入明确；
- 输出明确；
- 失败时给出可定位的错误信息；
- 避免吞掉错误或只输出模糊的“失败”；
- 对关键路径打印实际文件名、大小或版本等非敏感信息。

不要为了步骤数量而过度拆分。目标是让失败定位更快，而不是让工作流更复杂。

## 6. 外部依赖与供应链可靠性

### 6.1 固定依赖来源

对 CI 自动下载的外部组件，尽量明确：
- 来源仓库/发布者；
- 固定版本、Release tag 或 commit；
- 具体资产文件名；
- 下载 URL；
- SHA-256 或其他可信校验值；
- 许可证和分发条件；
- 目标架构和预期文件。

避免使用未固定的 `latest`、模糊通配符或会随时间变化的下载地址。若上游资产不可用，应先确认来源和替代方案，不要静默切换到来源不明的文件。

### 6.2 下载后校验

推荐流程：
1. 下载到明确路径。
2. 检查文件存在且非空。
3. 校验 SHA-256。
4. 解压到临时目录。
5. 检查预期文件数量、文件名、架构和大小。
6. 复制到构建系统实际读取的目录。
7. 在打包后再次检查最终包是否包含它。

哈希匹配证明下载文件与指定摘要一致，不自动证明发布者可信、许可证允许分发或文件本身安全。来源审查和许可证检查仍然必要。

### 6.3 外部构建依赖与项目源码的边界

如果改造只需要把一个外部运行时组件集成进安装包/便携包，优先评估能否在 CI 中下载、校验和注入，而不是直接修改核心源码。只有当目标功能确实需要源代码适配时，才修改核心代码。

这能降低 Fork 与上游的长期差异，但不能把所有功能集成都简化为“只改 CI”；应以真实集成机制为准。

## 7. 架构矩阵与打包路径

涉及 x86/x64、ARM 等多架构时，不能只检查“文件存在”。

### 7.1 建立明确映射

对每个构建目标明确记录：
- 编译架构；
- 对应依赖文件；
- 运行时加载路径；
- 便携包中的目标路径；
- 安装包中的目标路径；
- 验证方式。

避免依赖文件名猜测架构，也不要把 32 位文件复制进 64 位目录。

### 7.2 验证文件进入最终产物

建议按层验证：
- 下载目录：预期文件是否存在、大小是否合理。
- 中间 staging 目录：是否复制到正确架构目录。
- 便携 ZIP：解压后是否包含正确路径和文件。
- 安装包：通过适当工具列出或提取安装包内容，检查内部目标路径。
- 运行时：软件是否能加载该组件，界面或日志是否能确认实际使用了目标组件。

**只验证安装程序 EXE 存在且非空，不等于验证了安装包内部内容。** 如果没有提取安装包或用安装器脚本与构建日志进行可验证的交叉检查，应明确标记为“安装包内部文件尚未独立验证”。

## 8. Artifact 与最终交付验证

### 8.1 不止看 Artifact 数量

检查：
- Artifact 名称、数量、下载链接和过期时间。
- 每个目标文件是否存在且非空。
- 文件大小是否合理，是否出现意外的 0 字节文件。
- ZIP 能否完整解压，是否存在损坏。
- 内部目录结构和关键文件是否正确。
- x86/x64 包是否放入对应架构的文件。
- 是否包含意外调试文件、临时文件或多余目录。

### 8.2 哈希与可追溯性

对最终交付文件可记录 SHA-256，方便用户核对下载完整性。建议同时记录：
- Workflow Run URL；
- Run ID；
- 构建 commit SHA；
- Artifact ID/名称；
- 目标文件名、大小和 SHA-256；
- Artifact 到期时间（如有）。

不要将外层 Artifact 下载包的哈希误认为其中每个安装包/便携包的哈希。应明确每个摘要对应哪个文件。

### 8.3 运行时验收

根据软件类型设计最小关键测试：
- 安装版：安装、启动、基本功能、卸载或升级行为。
- 便携版：解压即用、配置目录、依赖加载、不同路径启动。
- 插件/渲染器/编解码器：确认实际被程序识别和使用，而不是只确认文件在目录里。
- 多架构：在对应目标环境或兼容环境中分别验证。

由用户完成实际环境测试时，记录用户反馈和测试版本。没有真实运行验证时，不要写“软件一切正常”。

## 9. 变更记录与证据管理

每个重要问题建议记录：
- 现象和影响范围；
- 观察到的事实；
- 排除过的可能原因；
- 最终根因及证据；
- 修改文件和 commit；
- 修改前后 CI Run；
- Artifact 验证结果；
- 尚未覆盖的验证层级；
- 用户验收结论。

区分“事实”“推断”和“待验证”。例如：
- 事实：该次 Run 没有创建 Job。
- 推断：问题可能发生在工作流解析或触发阶段。
- 根因：只有找到具体无效 YAML 片段并修复后成功验证，才能这样表述。

不要把时间上的先后关系当成因果证据。

## 10. MPC-HC 案例复盘：可迁移经验与专属事实

### 10.1 本次实际改造

项目：`shenshou/mpc-hc-next`  
上游：`clsid2/mpc-hc`  
开发分支：`develop`

本次目标是在便携版和安装版中集成 MPC Video Renderer（MPCVR），尽量不改动 MPC-HC 核心源码。

最终集成的 MPCVR 版本为 0.11.2.2638，来源为 `qwerttvv/Player` 的 nightly 构建资产，而不是将其描述为 MPCVR 官方上游发布。CI 固定了发布资产和 SHA-256，并检查下载文件、架构文件和便携包内容。

### 10.2 Actions 故障与修复

- Run #16–#19：运行失败，页面没有 Job、步骤日志和 Artifact。
- 排查时没有直接修改 MPC-HC 源代码，也没有把问题归咎于编译器。
- 最终检查发现 `.github/workflows/build.yml` 文件尾部存在重复且破坏结构的片段。
- 清理提交：`c4f0ce176acf12eea5c51e43023bcf3058ff84e0`。
- Run #20 使用该提交成功执行 x86/x64 Release Job。
- 日志确认下载的 x86/x64 MPCVR 文件已准备，并分别加入对应便携包。
- 下载并解压 Artifact 后，确认 x86 ZIP 包含 `MPCVR/MpcVideoRenderer.ax`，x64 ZIP 包含 `MPCVR/MpcVideoRenderer64.ax`。
- 用户最终实际测试软件，确认运行正常。

该案例没有独立提取安装程序并检查其内部文件清单，因此“便携 ZIP 内容已直接检查”与“安装包通过构建脚本和日志确认打包流程”必须区分。用户后续实际测试正常，完成了用户侧软件验收，但不能反向声称曾执行过未执行的安装包内部提取检查。

### 10.3 可迁移经验

- Job 为 0 时，优先调查工作流识别、YAML 结构和触发条件，不要直接改业务源码。
- 检查整个工作流文件，尤其是文件尾部；重复残片可能破坏整个 YAML。
- 每次重跑必须有明确假设和对应修改。
- 固定外部依赖版本与摘要，并验证架构文件。
- 追踪依赖从下载目录到最终包的完整路径。
- 便携包要实际解压检查；安装包要单独验证内部内容。
- 区分 CI 成功、Artifact 正确和用户运行验收。
- 保留用户明确的改造边界，不为“顺便优化”扩大范围。

### 10.4 不应直接复制的项目专属信息

以下属于 MPC-HC/MPCVR 案例，不是其他 Fork 项目的默认方案：
- MPC-HC 的源代码目录、内部过滤器加载逻辑和安装器脚本路径。
- MPCVR 的具体版本、下载仓库、资产名称和哈希。
- x86/x64 的特定文件名和目标目录。
- Windows 2022 Runner、Visual Studio、Inno Setup 等构建环境选择。
- 本次工作流的具体步骤和 Artifact 命名。

新项目必须重新调查自己的构建系统、依赖来源、架构和分发方式。

## 12. 如何使用本文

- 新接手 Fork 时，先使用第 3、4、11 节建立调查和排障路径。
- 修改 CI 时，重点使用第 4、5、6 节。
- 集成外部依赖或多架构产物时，重点使用第 6、7、8 节。
- 不要把 MPC-HC 的目录、工具链、依赖和步骤直接复制到其他项目。
- 根据项目风险裁剪检查项；小项目不需要引入不必要的流程和工具。
- 每次新项目完成后，只把已验证、可迁移的经验补充到通用章节；项目专属事实留在案例复盘中。

**最终原则：先理解项目，再做最小改动；先定位失败层级，再修复；验证最终交付物，而不止验证构建日志；只陈述已经有证据支持的结论。**
